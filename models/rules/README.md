# models/rules/ — 规则评分（财务逾期 · 设备健康）

## 技术栈
PostgreSQL 向量化 SQL · YAML 阈值配置 · Python 薄封装

## 职责
两个**有意不使用机器学习**的评分场景。

## 为什么规则比模型更合适

| 场景 | 用规则的理由 |
|---|---|
| 财务逾期 | 账龄阶梯是行业共识标准，模型反而引入不可解释性；财务人员需要能自己核对 |
| 设备健康 | 扣分项（故障次数、漏检、停机时长）需与设备部门逐条对数，模型输出无法对齐 |

> 这不是技术能力不足，而是**交付可信度**的主动选择。汇报时应明确说明这一取舍，
> 这本身就是"懂业务"的体现。

## 放什么代码

| 文件 | 内容 |
|---|---|
| `score_finance.sql` | 财务逾期规则评分（账龄、到期日、未回款金额、历史回款及时性） |
| `score_equipment.sql` | 设备健康规则评分（故障次数、停机时长、漏检、维修间隔、能耗偏离） |
| `thresholds.yml` | 评分阈值与权重配置（业务方可调，无需改代码） |
| `runner.py` | 执行 SQL、写入 ADS 结果表 |

## 评分模型示例（设备健康）

| 扣分项 | 权重 | 依据 |
|---|---|---|
| 近 30 天故障次数 | 每 1 次扣 10 分，最多 30 | 频发故障设备优先关注 |
| 累计停机时长 | 每 10 小时扣 5 分，最多 25 | 衡量对生产的实际影响 |
| 点检漏检次数 | 每 1 次扣 5 分，最多 15 | 维保执行到位的间接指标 |
| 维修间隔偏离 | 偏离标准间隔 20% 以上扣 10 分 | 早期劣化信号 |
| 能耗基线偏离 | 偏离基线 15% 以上扣 20 分 | 设备效率下降的直接体现 |
| **健康等级** | ≥90 优 / 75~89 良 / 60~74 关注 / <60 重点 | — |

## 干什么事情
1. 所有阈值集中在 `thresholds.yml`，业务方调整无需开发介入（演示可现场改阈值看效果变化）
2. 这些规则**同时被 dbt test 覆盖**（如健康分必须在 0~100），保证规则本身不出错
3. 评分明细含每一扣分项的实际值与扣分，报表可展示"扣分构成"——比一个总分更有说服力
