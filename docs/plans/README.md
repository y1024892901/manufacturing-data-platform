# 十系统完善计划

> 制定于 2026-09-22 · 现状依据 [current-status.md](../current-status.md) · 验收标准依据 [system-functional-catalog.md](../system-functional-catalog.md)

## 为什么需要拆分

按 [current-status.md](../current-status.md) 的验收矩阵，**十个系统目前没有任何一个达到「系统本职完成的最低验收」五项**。缺口规模：

| 验收项 | 已达标 | 还差 |
|---|---|---|
| ① ≥5 个本职模块 | 0 | **10 个**（MES、能源是从零建） |
| ② ≥3 类单据到终态 | 2（QMS/WMS） | **8 个** |
| ③ 审批 + 异常闭环 | 2（MDM/PLM） | **8 个** |
| ④ ≥2 个幂等事件 | 3 | **7 个**（且消费侧全部为空） |
| ⑤ 运营报表 | 0 | **10 个** |

现有代码 142 个 Java 文件、204 个端点；补齐需再加约 400–600 个文件。**必须拆分成多个可独立验证的计划**——一次改几百个文件既无法评审，也无法定位问题。

## 执行顺序

```
00 横向地基 ──┬── 02 MDM+PLM ──┐
              ├── 03 QMS+WMS ──┤
              ├── 04 ERP+CRM ──┼── 08 前端与报表
              ├── 05 SRM+EAM ──┤
              ├── 06 MES ──────┤
              └── 07 能源 ─────┘

01 缺陷修复（可随时插入，建议最优先）
```

**为什么 00 要排在前面**：鉴权、事件消费、单据终态、实体同步这四项在 10 个系统里是**同一件事**。先在 00 里立好模板，后续每个系统直接套用；反过来先做各系统，会在每个系统里重复解同一道题。

**为什么 01 建议最优先**：23 条缺陷中有 4 条导致**现有功能根本跑不通**（详见 [01-bugfix.md](01-bugfix.md) 的「优先修复」一节）。半轮的成本就能让已写好的代码真正可用，投产比高于铺新代码。

## 交付约定

每个计划完成后应满足：

1. 该计划「完成标准」一节的全部条目可勾选；
2. 受影响的模块 `STATUS.md` 同步更新（完成度、接口清单、验收对照）；
3. `docs/current-status.md` 的总览表与验收矩阵同步更新；
4. 新增的数据库变更走 Flyway 迁移（`V39+`），不再改动 `infra/db-init/`（该通道截至 V11 已 baseline）。

> 注意：EAM、能源、MES 三者的表由 `infra/db-init/05_business_systems_2.sql` 创建，属 V1–V11 通道。给它们**加字段**应从 `V39` 起新开迁移脚本。
