# ai/ — AI 能力层（原方案最大空白的填补）

## 技术栈
Python 3.11 · **DeepSeek / 千问（Qwen）** 在线 API · **MCP (FastMCP)** · **Agent Skills** 规范 · pgvector · FastAPI（SSE 流式）

## 职责
把数仓能力变成 AI Agent 可以自主使用的工具，让"数据 → 洞察"这一步自动化。

> **原方案在这一层只有一句承诺**（"沉淀可供 AI Agent、Skills 和 FDE 人员使用的可信数据与业务语义基础"），
> 没有任何组件。本目录是该承诺的落地实现。

## 三个组件的确切边界（避免职责混淆）

| 组件 | 是什么 | 解决什么 | **不做什么** |
|---|---|---|---|
| **语义层 + pgvector** | 业务口径、SOP、指标定义的向量化存储 | 让 AI 知道"齐套率"到底怎么算 | 不做检索之外的逻辑 |
| **MCP Server** | 数仓能力的工具化网关 | 权限、审计、口径的**唯一收口** | **绝不直连数据库给 AI** |
| **Skill** | 高频分析动作的封装 | 把"怎么做"沉淀为可复用能力 | 不重复 MCP 的原子能力 |
| **Agent** | 多工具自主编排 + 归因 | 从现象追到原因，给建议 | 不产生新的数据口径 |

## 核心设计原则

### 原则一：MCP 只暴露工具，绝不暴露数据库连接

```
❌ 错误做法：把数据库连接串给 AI，让它自由写 SQL
✅ 正确做法：AI 只能调用 9 个受控工具，每个工具都有权限校验与审计日志
```

**带来的三个收益**：① 权限可控（只读账号 + 表白名单）；② 口径可控（指标走 `query_metric`，AI 算不错）；③ 每次调用可审计（合规演示点）。

### 原则二：常规问题走口径工具，探索问题才走 SQL

| 工具 | 适用 | 特点 |
|---|---|---|
| `query_metric` | "本月按期交付率是多少" | 口径锁死，AI **不可能**算错 |
| `run_sql` | "上个月哪 10 张订单的报工记录最异常" | 灵活但受限（白名单 + 强制 LIMIT + 审计） |

这直接实现原方案 7.1 节"统一指标保证智能问答读取的数据可信、口径一致"。

### 原则三：数字准确靠代码，表达流畅靠 LLM

归因文案中的数字、比值、结论由模板或 SQL 生成，LLM 只做**润色与建议扩展**。
失败时回退到模板原文。**反过来让 LLM 自由生成数字，演示现场必然翻车。**

### 原则四：双供应商自动降级（演示兜底）

主供应商（DeepSeek）超时或限流 → 自动切备用供应商（千问）。演示不会因单一 API 抖动中断。

## 干什么事情
1. 让 AI 读懂数仓（语义层）
2. 让 AI 安全用数仓（MCP 工具）
3. 让 AI 做重复分析（Skills）
4. 让 AI 自主追因（Agent）
