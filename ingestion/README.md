# ingestion/ — 数据采集接入

## 技术栈
Python 3.11 · **dlt**（data load tool）· psycopg2 · watermark 增量 · APScheduler（轻量触发）

## 职责
把 9 类源系统的数据稳定、可追溯、可重跑地搬进 ODS 层。

> **替代了原方案的 DataX**。理由：DataX 是 XML 配置 + Java 进程，新增一张表要改一次配置；
> dlt 用装饰器声明，schema 演化自动处理，且与 Python 生态无缝集成。

## 放什么代码 / 文件

```
ingestion/
├── connectors/      各源系统的连接定义与抽取器
├── pipelines/       dlt 管道定义（source → resource → destination）
├── loaders/         写入 ODS 的落地逻辑与批次管理
├── watermark/       增量位点管理（读取、更新、回滚）
└── run.py           采集入口（支持全量/增量/指定表）
```

## 采集模式

| 模式 | 触发 | 行为 |
|---|---|---|
| 全量初始化 | 首次接入新系统 | 清空 ODS 对应表并全量导入 |
| 增量同步 | 定时 / 手动 | 按 `updated_at > watermark` 抽取 |
| 单表重跑 | 排障 | 指定表 + 时间窗重抽，覆盖该窗口分区 |
| 影子同步 | 新增表验证 | 只比对不落库，输出差异报告 |

## ODS 落地的四个审计列（每张 ODS 表必备）

| 列名 | 含义 | 用途 |
|---|---|---|
| `_batch_id` | 批次 UUID | 追溯"这批数据是哪次采集来的" |
| `_src_system` | 来源系统标识 | 跨系统溯源 |
| `_extract_ts` | 抽取时间戳 | 时效性监控 |
| `_row_hash` | 业务字段哈希 | 幂等去重、识别变更行 |

## 干什么事情
1. 读取管理后台登记的元数据（系统、表、字段、同步策略）决定采什么、怎么采
2. **原样落地**：不转型、不清洗、不修改任何业务值——清洗是 DWD 的职责
3. 每次采集写入 `ops.ingest_run_log`：表名、起止时间、抽取行数、写入行数、状态、错误信息
4. 失败自动重试 3 次（指数退避），仍失败则告警并在管理后台标红
