# apps/admin/ — 管理后台（原方案完全缺失的核心模块）

## 技术栈
FastAPI + SQLModel · Alembic（迁移）· Pydantic v2 · 独立 `platform_meta` 库

## 职责
**"维护各个系统的地方"** —— 让平台从"写死的演示"变成"可配置的产品"。

## 核心设计：元数据驱动

```
管理员在后台登记  →  元数据落库  →  驱动采集与建模  →  全链路自动适配
   （配置动作）       （数据）        （自动执行）        （无需改代码）
```

**这是"表数量不固定"需求的技术解法：** 新增系统/表只是新增元数据记录，不是新增代码。

## 放什么代码 / 文件

```
apps/admin/
├── models/        元数据模型（SQLModel 表定义）
├── routers/       管理接口
├── services/      同步触发、血缘刷新等业务动作
└── migrations/    Alembic 迁移脚本
```

## 元数据模型（七张核心表）

| 表 | 一行 = 什么 | 关键字段 |
|---|---|---|
| `sys_system` | 一个来源系统 | 系统编码、名称、类型、负责人、连接配置、状态 |
| `sys_table` | 一张源表 | 表名、所属系统、业务域、主键、水位线列、同步策略、行数、状态 |
| `sys_column` | 一个字段 | **源字段名、目标字段名、中文业务含义**、类型、是否主键、是否敏感、是否在分析范围 |
| `sys_sync_task` | 一个同步任务 | 表名、模式（全量/增量）、调度、上次运行、状态、行数 |
| `sys_rule` | 一条治理规则 | 规则编号、表名、规则类型、表达式、严重级别、处理动作、命中数 |
| `sys_metric` | 一个指标 | 指标名、中文名、**口径定义**、分子分母、维度、负责人 |
| `sys_audit_log` | 一次操作 | 操作人、操作类型、对象、变更前后、时间 |

## 后台功能页面

| 页面 | 功能 |
|---|---|
| **概览** | 系统数、表数、今日同步次数、质量通过率、待处理问题 |
| **系统管理** | 新增/编辑/停用来源系统，测试连接，查看系统概览 |
| **表管理** | 表清单、字段明细、同步策略配置、手动触发同步 |
| **字段映射** | **逐字段填写中文业务含义**（这是数据字典的语义来源） |
| **同步监控** | 任务状态、运行历史、失败重跑、行数波动趋势 |
| **规则管理** | 治理规则 CRUD、试运行、命中数与问题下钻 |
| **指标管理** | 指标口径 CRUD、指标预览、口径变更记录 |
| **血缘查询** | 交互式血缘图，支持上下游追溯与列级查看 |
| **质量看板** | 通过率、问题分布、治理前后对比 |
| **模型管理** | 模型版本、评估指标、手动重训、版本对比 |
| **审计日志** | LLM 调用与 SQL 调用审计记录 |
| **用户权限** | 角色、权限、操作记录 |

## 关键约束

| 约束 | 说明 |
|---|---|
| **元数据库与数仓物理隔离** | 元数据在 `platform_meta` 库，dbt 在 `warehouse` 库，互不影响 |
| **变更留痕** | 所有元数据变更写 `sys_audit_log`，可追溯"谁在什么时候改了什么" |
| **配置即生效** | 元数据变更后，采集管道下次运行时自动生效（配置驱动设计） |
| **敏感字段标记** | 标记为敏感的字段在 API 与 MCP 返回时自动脱敏 |

## 干什么事情
1. 让非开发人员也能配置数据接入（FDE 人员可独立操作）
2. 元数据同时是**数据字典的来源**，配置完自动生成文档
3. 元数据变更驱动采集与建模，**新增系统零代码**
4. 演示亮点：现场新增一个系统与 3 张表，几分钟内走完全链路
